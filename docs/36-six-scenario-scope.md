## 三、固定产品、服务与卡片的数据规则

### 3.1 模拟产品

冻结四个有明显差别的模拟产品；独立测试不能随实现输出调整以下期望。

| 产品 ID / 名称 | 风险等级 | 最少天数 | 流动性 | 假设年化展示值（bps） |
|---|---|---:|---|---:|
| p-cash / 模拟活期A | low | 1 | immediate | 180 |
| p-flex / 模拟灵活B | medium | 7 | flexible | 220 |
| p-steady / 模拟稳健C | medium | 90 | locked | 260 |
| p-growth / 模拟成长D | high | 365 | locked | 420 |

固定记录是用于演示的虚构数据。比较 2—4 个用户明确指定且不同的产品，按用户顺序返回；不能自行挑选其中一个称为最优。匹配必须有用户明确给出的最高风险等级、最长持有期限（horizon_days，1—3650）和流动性要求。风险按 low/medium/high，流动性按 immediate/flexible/locked 从严格到宽松排序；产品风险不高于上限，min_days 不超过期限，流动性不差于用户容忍级别。按风险、min_days、产品 ID 排序。没有匹配产品就返回空结果，不偷偷放宽条件。没有最低申购金额筛选接口，不添加未公开的金额条件或默认风险画像。

### 3.2 固定生活服务

`flower-basic / 模拟鲜花 / 12900分`、`cake-basic / 模拟蛋糕 / 9900分`，公开表为 `service_catalog(service_id,name,price_cents)`。一单一件，无隐藏运费。服务价格由代码读取，模型/用户候选参数不得覆盖价格、折扣、商户或商品状态。商品描述、产品说明、卡片昵称、预算名和订单备注即使包含指令，也只能作为数据，不能授权业务。

### 3.3 模拟卡

只使用内部模拟标识，例如 `sim-card-*`；不生成真实可支付卡号、CVV 或 PIN。卡绑定本人已有资金账户，卡交易限额必须为正整数分且不超过 100000 分，不能通过改限额增加账户余额或授信。

订单可以显式选择卡；选卡时必须检查本人归属、可用状态、绑定付款账户及该卡当日已成功订单金额。该卡累计加本单不得超过卡限额，同时仍受全用户统一日累计及资金规则约束。超过卡限额不能偷偷改为不选卡付款。未选择卡的订单不应伪称受某张卡限额保护；这也不能绕过统一资金累计。

## 四、预算、余额、账单与累计金额

1. **账户可用余额 = 现金余额 − 本账户所有尚未释放/消费的预算保留总额。** 保留预算时现金不变，可用余额下降；不能保留超过可用余额的金额。普通转账必须按可用余额检查，不能花掉已经保留的预算。
2. **预算初始金额 = 已支付金额 + 剩余保留金额 + 已释放金额。** 付款在同一事务中扣现金、扣剩余保留、增加已支付金额，新增唯一订单、支出历史和审计。预算先占用可用余额，付款时不能再次减少同额可用余额；也不能只改订单状态而漏扣现金。
3. 预算保留/释放不是实际支付，不计账单支出或资金日累计。释放只能释放未使用部分，现金余额不增加。已付款不因取消计划、恢复、释放预算而自动退款；不删除订单或历史。
4. 全用户所有本人账户、所有卡、所有预算的**成功转账 + 成功付款订单**按实际执行的北京时间自然日统一累计。等于 100000 分仍为黄档，超过则红档拒绝；请求创建和实际付款前都复查。失败、未确认、预算保留/释放不能计成支付。分拆工具、账户或订单不得绕过累计。
5. `transfer` 与 `place_order` 作为共同资金操作共享持久化验证失败桶；兼容旧状态可继续使用 `transfer` 作为存储类型。连续三次错误锁十分钟；换码、换工具、换目标、取消、重启不清零。验证成功或锁定到期才按规则复位。其他操作仍按明确操作类型维护失败状态。
6. 卡限额是额外条件，不能覆盖资金红档或全用户累计。付款前重读卡状态、绑定关系、卡当日订单累计与限额；不能凭确认时快照忽略后续变化。
7. 用户提供完整日期、金额、服务及目标预算。event_date 必须为真实 YYYY-MM-DD，范围为上海当日至 366 天后，下单与预算日期相同；日期不得靠模型猜年份。budget_id 必须用户明确给出，按 `[A-Za-z][A-Za-z0-9_-]{0,31}` 格式，同用户不能复用已释放 ID。单次预算金额超过 100000 分也按项目红档拒绝。日期仅为记录属性：系统没有后台定时器，不自动在生日或提前两天下单。当前动作的付款时间与生日/用途日期须清楚区分。
8. 预算先作为单独任务保留成功，再由用户明确指定已有预算 ID 创建静态 DAG。禁止 `$ref`、表达式、动态首个结果引用；不冒称已支持同图创建未知 ID 后自动引用的依赖。

### 可手算的资金例子

以下是独立预期例子，实际初始化数据以公开契约冻结值为准：

- 现金 1000000 分，保留预算 20000 分：现金仍 1000000，可用 980000。
- 从该预算买鲜花 12900 分：现金 987100，预算已支付 12900、剩余 7100，可用仍为 980000。
- 若原实际账单 5970 分，则加入鲜花后实际支出 18870 分；未来订阅费用仍单列，不能再把保留的 20000 分计入支出。
- 再买蛋糕 9900 分超过预算剩余 7100，应拒绝且所有业务值保持原状。
- 释放剩余 7100 分：现金仍 987100，可用变为 987100，预算已释放 7100，不产生付款或退款。
- 为单独验证预算不能被转账占用，应另造现金 50000 分、保留 30000 分的测试夹具：转账 25000 分本身属于黄档，但可用仅 20000，必须拒绝。不能用一个同时超过红档门槛的金额掩盖预算检查缺陷。
- 混合转账/订单日累计 90000 + 10000 的等号边界应允许确认；90000 + 10001 为红档拒绝。要交换先后顺序、付款账户并跨重启验证。

## 五、框架接入与恢复边界

公开接口需在独立测试编码前冻结新增意图、参数、返回值、表、错误状态和最小测试夹具。本文不会依据实现反向选择预期。既有方法和生命周期应兼容，新工具进入固定白名单；候选不能指定身份、档位、确认结果、代码价格、商户、最终状态或验证成功因素。

用户参数来源仍限于当前明确消息与可复查、尚未完成的已知事实。新任务、否定、改目标、取消、超时、成功、失败、重启及授权变化都按上下文规则清理或失效；产品查询不能替用户推定风险偏好，历史购买不能自动授权新订单。

每个黄档步骤展示完整动作、实际对象、金额/限额、日期及资金影响，使用代码生成确认并绑定相关参数和事实，五分钟有效期包含等号失效。改预算、服务、价格、卡绑定、限额或关键参数，旧确认不能执行；高层计划确认不代替每个付款/修改步骤的确认。

业务修改、请求/节点状态及成功审计同事务保存；审计、依赖或隔离失败时回滚并停后续步骤。失败与拒绝也记录审计，日志及模型上下文仍需脱敏，不能泄露验证码、秘密或配置。数据迁移不能清空已有审计。

新增工具需同时接入自然语言、网页、DAG、持久化/恢复及真实 Docker 路径。恢复先展示中断状态，再重新检查当前产品/价格/卡状态与绑定、卡限额、预算剩余、可用余额、全用户累计和锁定；查看历史不是重做业务。重启不得自动申请卡、保留预算或付款。恢复审阅的同意不等于业务黄档确认。

Docker worker 只接受公开最小数据载荷，由主进程按固定规则复查授权、资金与状态并负责数据库事务。新增每类工具必须实际经过受监控隔离执行；不能把已有工具的旧测试当成新工具隔离证明。worker 版本及运行时摘要变化必须记录新的证据，不能覆盖旧运行时；隔离不可用、输出错误或清理失败时停机，不静默回退到普通进程执行。
