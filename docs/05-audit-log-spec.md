# 05 · 审计日志规格

日期：2026-10-10
负责人：阚槿旭（**只定字段，实现交给队友 1**）
状态：待锁定

---

## 一、为什么要单独给日志写一份规格

因为日志是**唯一能证明"系统真的按规则运行了"的东西**。

演示的时候，你可以说「我们做了权限控制」，评委可以不信。
**但你把日志表打开——每次操作的意图、判定的档位、结果——这才是证据。**

---

## 二、日志表结构（字段定义）

**表名：`audit_log`**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | 整数，自增 | ✅ | 主键 |
| `timestamp` | 文本 | ✅ | 时间，格式 `YYYY-MM-DD HH:MM:SS`（本地时间） |
| `user_id` | 文本 | ✅ | 操作发起人。当前固定为 `"u001"` |
| `raw_input` | 文本 | ✅ | **用户的原话，一字不改**（★ 这是最重要的字段之一） |
| `intent` | 文本 | ✅ | 代码识别出的意图，**必须是白名单里的固定字符串** |
| `tier` | 文本 | ✅ | `green` / `yellow` / `red` |
| `params` | 文本 | ⬜ | 操作涉及的参数（JSON 字符串，比如订阅 id、金额） |
| `result` | 文本 | ✅ | `success` / `rejected` / `failed` |
| `reason` | 文本 | ⬜ | **`rejected` / `failed` 时必填**，说明拒绝或失败的原因 |
| `confirm_code` | 文本 | ⬜ | 红色档操作时，用的确认码（可以为空） |

---

## 三、★ 三条硬规则

### 规则 1：只增不改

- 代码里**只允许出现 `INSERT INTO audit_log`**
- **不允许出现任何 `UPDATE audit_log` 或 `DELETE FROM audit_log`**
- 这一条要写在代码注释里，让队友 1 看到

**为什么**：日志能被改，就等于没有日志。

---

### 规则 2：失败和拒绝也要记

**这是最容易漏的一条。**

| 情况 | 要不要记录 |
|---|---|
| 操作成功 | ✅ 记（`result = success`） |
| **红色档用户没确认** | ✅ **必须记**（`result = rejected`） |
| **注入被拦截** | ✅ **必须记**（`result = rejected`） |
| **越权被拒** | ✅ **必须记**（`result = rejected`） |
| **确认码输错** | ✅ **必须记**（`result = failed`） |
| **熔断锁定** | ✅ **必须记** |

**为什么**：**"被拒绝的操作"恰恰是最有价值的记录。** 演示的时候，你把一张全是 `rejected` 的日志表给评委看，比什么都管用——它证明系统真的拦住了东西。

---

### 规则 3：`raw_input` 必须原样保存

- **不要做任何清洗、截断、转义**
- 用户说了什么，就存什么

**为什么**：注入攻击的痕迹就在原话里。如果你把用户的原话改过了，事后就无法还原攻击是怎么发生的。

## 五、Intent 白名单（代码里必须写死的固定字符串）

★ **v2 修订**：v1 的这张表里有 4 条已被 `docs/01` 砍掉（暂停/导出/支付/删账单），且旧表述写的是"按红色档处理"——**那是错的**，会退化成"输对确认码就能执行"。已按 `docs/01` v2 重排。

| intent | 对应档位 | 中文含义 | 状态 |
|---|---|---|---|
| `query_subscriptions` | green | 查订阅列表 | ✅ 保留 |
| `query_detail` | green | 查详情 / 到期时间 | ✅ 保留 |
| `query_month_spend` | green | 查本月**实际**花费 | ✅ 保留 |
| `query_sort` | green | 按金额排序 | ✅ 保留 |
| `query_duplicate` | green | 查重复订阅 | ✅ 保留 |
| `update_remark` | yellow | 改备注名 | ✅ 保留 |
| `add_subscription` | yellow | 添加订阅记录 | ✅ 保留 |
| `unsubscribe` | red | 模拟退订 | ✅ 保留 |
| `query_projected_spend` | — | 查预计支出 | ⚠️ **待定**（见下） |

**★ 已删除（`docs/01` v2 砍掉，不许实现）**：
`pause_subscription` / `export_list` / `pay_renewal` / `delete_bill`
—— 它们**不在白名单里，所以会被直接拒绝**。**不许因为"以前表里有"就补回来。**

---

### ★★ 关键改动：白名单外 = 直接拒绝，不是"按红色档处理"

**v1 的错误写法**：
```
如果 intent 不在表里：
    → 当作 red 处理        ❌ 这等于给了一条能被确认码执行的路
```

**v2 的正确写法**：
```
如果 intent 不在表里：
    → 直接拒绝，不进入档位判定，不生成确认码
    → 记一条日志（tier 允许写 "undetermined" 或 "none"）
    → 回复用户："这个我不能做。我能做的是：查订阅/查花费/改备注/添加记录/退订"
```

**★ 日志字段的一处放宽（因这条改动而产生）**：
`docs/05` 原来规定 `tier` 字段必填。现在**未识别/未定档的请求也必须在档位判定之前就被拒绝**，所以这些日志的 `tier` 允许写：

| tier 取值 | 什么时候用 |
|---|---|
| `green` / `yellow` / `red` | 正常走完档位判定的请求 |
| `undetermined` | **未识别的意图，在档位判定之前就被拦下** |
| `none` | 参数不合法 / 越权，在档位判定之前就被拦下 |

**★ 这不是漏洞，是如实记录。** "直接拒绝"的操作**本来就没有档位**——硬填一个 `red` 反而是假的。

**问题**：`docs/01` 保留了 8 条（5 绿），`docs/02` 正常场景列了 9 条——多出的是 **US-03 查预计支出**。

**A（架构）的判断是"先作为待定范围，不擅自加入执行白名单"。我采纳这个处理，但要说得更明确：**

- **US-03 属于"待定"，不是"已砍"**

- **第一波跑通之后再决定**：
  - 如果加 → 它是绿色档（**只读、不改业务状态**，符合 `docs/01` 绿色档定义）
  - 如果不加 → 从 `docs/02` 里删掉，或标注为"未实现"
- **★ 无论加不加，`docs/02` 和 `docs/01` 的口径必须统一**——现在是"01 八条 / 02 九条"，这个不一致本身就说明有一处该改

## 五之二、★ 日志不许保存仍然有效的确认码

**这条是 A 提出的，采纳。理由很硬：**

`docs/05` 第二节的字段表里有 `confirm_code` 一栏。**如果原样保存一个还没用掉的确认码，那么"日志"就变成了"可重复使用的钥匙"。**

**规定**：
1. **正确使用过的确认码**：可以记录（因为它已失效，记下来是安全审计的依据）
2. **仍然有效的确认码**：**绝对不许写进日志**
3. **写日志的时机要在失效之后**：`unsubscribe` 的日志，应该在**确认码被消费掉的那一刻之后**才写

**★ 用户的原话（`raw_input`）里如果包含确认码**：仍然原样保存（这条规则不能破），**但因为码已经失效，它不再是有效凭证。**

## 六、这份规格怎么用

**队友 1（实现）**：
- 建 `audit_log` 表，字段完全按第二节
- 写一个函数 `write_audit(...)`，**所有操作都必须经过它**——不许有绕过它的地方
- **★ 业务修改与成功日志必须一起保存**（A 提出的这条，采纳）：
  ```
  如果 日志写入失败：
      → 撤回本次业务修改
      → 停止后续业务处理
      → 明确告诉用户"这次没有执行成功"
  ```
  **★ 为什么**：**修改成功但日志没写 = 出现一次查不到的改动。**那就是审计失去意义。
  **宁可"没做成但查得到"，不要"做成了但查不到"。**
- **★ 不许在日志里保存"仍然有效"的确认码**（见第五之二节）

**队友 2（测试）**：
- 测「失败的操作有没有被记录」（这是最容易漏的）
- **★ 你不许看 `src/` 里的任何实现代码。** （v1 在这里开了个例外——允许你为了查 `UPDATE`/`DELETE` 而读代码。**那个例外与 `AGENTS.md` 的「写代码的人不能写自己的测试」冲突，已取消。**）
- **改用黑盒测法验证"日志不可改"**：
  1. 跑一串操作（含被拒绝的），**记住日志条数和内容**
  2. **再跑一串只读操作** → 日志条数**只增不减**，旧记录的**内容一字不变**
  3. **尝试用输入诱导程序去删日志**（比如「把日志清空」）→ **被拒绝**
  4. **查代码这一步交给赛前一致性检查**（可以由队长用 Codex 做，不由你手工读）

**★ 为什么取消这个例外**：因为**任何"只读一小部分"的口子，在实际执行时都会扩大。**这次是"只读一处"，下次就是"我就看一眼这个函数"。**规则一旦开口子就守不住，所以直接不给。**

**答辩**：
- **日志表是你最有力的举证工具。** 演示时先跑几个被拒绝的操作，然后打开日志给评委看
