## 一、为什么要单独给日志写一份规格

因为日志是**唯一能证明"系统真的按规则运行了"的东西**。

演示的时候，你可以说「我们做了权限控制」，评委可以不信。
**但你把日志表打开——每次操作的意图、判定的档位、结果——这才是证据。**

---

## 二、日志表结构（字段定义）

**表名：`audit_log`**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | 整数，自增 | ✅ | 主键 |
| `timestamp` | 文本 | ✅ | 时间，格式 `YYYY-MM-DD HH:MM:SS`（本地时间） |
| `user_id` | 文本 | ✅ | 操作发起人。当前固定为 `"u001"` |
| `raw_input` | 文本 | ✅ | **用户的原话，一字不改**（★ 这是最重要的字段之一） |
| `intent` | 文本 | ✅ | 代码识别出的意图，**必须是白名单里的固定字符串** |
| `tier` | 文本 | ✅ | `green` / `yellow` / `red` |
| `params` | 文本 | ⬜ | 操作涉及的参数（JSON 字符串，比如订阅 id、金额） |
| `result` | 文本 | ✅ | `success` / `rejected` / `failed` |
| `reason` | 文本 | ⬜ | **`rejected` / `failed` 时必填**，说明拒绝或失败的原因 |
| `confirm_code` | 文本 | ⬜ | 红色档操作时，用的确认码（可以为空） |

---

## 三、★ 三条硬规则

### 规则 1：只增不改

- 代码里**只允许出现 `INSERT INTO audit_log`**
- **不允许出现任何 `UPDATE audit_log` 或 `DELETE FROM audit_log`**
- 这一条要写在代码注释里，让队友 1 看到

**为什么**：日志能被改，就等于没有日志。

---

### 规则 2：失败和拒绝也要记

**这是最容易漏的一条。**

| 情况 | 要不要记录 |
|---|---|
| 操作成功 | ✅ 记（`result = success`） |
| **红色档用户没确认** | ✅ **必须记**（`result = rejected`） |
| **注入被拦截** | ✅ **必须记**（`result = rejected`） |
| **越权被拒** | ✅ **必须记**（`result = rejected`） |
| **确认码输错** | ✅ **必须记**（`result = failed`） |
| **熔断锁定** | ✅ **必须记** |

**为什么**：**"被拒绝的操作"恰恰是最有价值的记录。** 演示的时候，你把一张全是 `rejected` 的日志表给评委看，比什么都管用——它证明系统真的拦住了东西。

---

### 规则 3：`raw_input` 必须原样保存

- **不要做任何清洗、截断、转义**
- 用户说了什么，就存什么

**为什么**：注入攻击的痕迹就在原话里。如果你把用户的原话改过了，事后就无法还原攻击是怎么发生的。

## 五、Intent 白名单（代码里必须写死的固定字符串）

**★ 只有这几个值。出现别的值 = 说明模型输出了不该有的东西 = 按红色档处理。**

| intent | 对应档位 | 中文含义 |
|---|---|---|
| `query_subscriptions` | green | 查订阅列表 |
| `query_total` | green | 查总额 |
| `query_detail` | green | 查某个订阅详情 |
| `query_duplicate` | green | 查重复订阅 |
| `update_remark` | yellow | 改备注 |
| `pause_subscription` | yellow | 暂停订阅 |
| `add_subscription` | yellow | 添加订阅 |
| `export_list` | yellow | 导出清单 |
| `unsubscribe` | red | 退订 |
| `pay_renewal` | red | 续费/支付 |
| `delete_bill` | red | 删除账单记录 |

**★ 实现要求**：
```
如果 模型输出的 intent 不在上面这张表里：
    → 当作 red 处理
    → 记录一条 rejected 日志
    → 回复用户 "我没理解你的意思，请换个说法"
```

**★ 为什么这么设计**：这是**白名单**，不是黑名单。**没被明确允许的，一律拒绝。** 这样即使模型出错了、被注入了、输出了乱七八糟的东西，结果也是安全的。

## 六、这份规格怎么用

**队友 1（实现）**：
- 建 `audit_log` 表，字段完全按第二节
- 写一个函数 `write_audit(...)`，**所有操作都必须经过它**——不许有绕过它的地方
- 严格按照第三节三条硬规则

**队友 2（测试）**：
- 测「失败的操作有没有被记录」（这是最容易漏的）
- 测「日志里有没有 `UPDATE` 或 `DELETE` 的痕迹」（可以读代码来找，但**只看这一处，不许看其他实现代码**）

**答辩**：
- **日志表是你最有力的举证工具。** 演示时先跑几个被拒绝的操作，然后打开日志给评委看
