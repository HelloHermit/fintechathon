## 输入、前置数据与固定期望

用例 `V2-PROC-01` 按规则 US-10、US-11、US-14、US-30、US-31 设计，已实际运行。

1. 每轮新建临时库，用公开夹具账户 `alice-main=1000000`、`alice-savings=500000`、`bob-main=100000` 分。
2. 仅通过公开 `propose`＋`confirm`，先从 `alice-main` 给联系人 `wang` 成功转出 `95000` 分；没有直接插入成功转账作为基线。
3. 两个子进程均使用可信测试身份 `alice`，各自构造服务和 SQLite 连接。双方准备完成后，通过三方 barrier 同步开始 `propose`：分别从 `alice-main`、`alice-savings` 给公开联系人 `wang` 转 `4000` 分。
4. 双方 `propose` 均完成后，再通过第二个三方 barrier 同步开始确认。仅在公开响应为 pending 且实际提供确认码时，才调用 `confirm`；不伪造待确认状态或有效码。
5. 父进程收齐两份实际结果后，先核对仍保持连接时的数据库，再共同释放 close 事件。两子进程收到事件后各自关闭连接，父进程 join 后再次核对数据库，最后删除临时库。

两次运行使用的业务测试时钟均为 `2026-10-11T12:00:00+08:00`，对应上海自然日。它只经公开测试构造参数传入，不是正式入口的调时钟能力；进程启动和调用时间差另用实际单调时钟记录。

固定期望为：每日同用户、跨账户成功转出总额不超过 `100000` 分；并发新增 40 元至多成功一笔；余额无负数，账户总额守恒；每个账户的余额变化恰好匹配成功转账，不能部分扣款或部分入账；成功 transfers 与 `transfer / executed / success` 审计逐个请求一一对应；新增成功交易记录按账户归属和金额绝对值匹配每笔转账的转出、转入双方。公开契约没有规定交易 `kind` 和金额正负表示法，测试没有依实现推导这些枚举。

新请求会使同用户旧 pending 失效，这是公开接口规则。允许两笔均未成功作为安全结果，但必须报告可用性代价，不能把零成功写成使用体验正常。该次实际每轮均成功一笔。

## 证明边界与最没把握处

最没把握的是这 10 轮同步调度没有覆盖的其他进程交错。barrier 同步的是 API 开始，不能保证数据库提交恰好同时发生。虽然两个 propose 实际都返回 pending，随后一个确认因新请求失效规则被拒绝，本次未证明两个仍有效授权都进入事务内重新判档的路径；也未把临时开发中的错误直接当成已完成版本漏洞。

源码哈希是有限时点快照，不是持续文件监控；若本次记录的前后／加载时点不一致，脚本会拒绝把混合版本报成统一通过。当前源码后续再改，则应以对应新哈希重跑该专项，不能继续用这份结果覆盖新版本。

本专项没有调用真实模型、浏览器、网络、MFA、真实银行或真实资金，没有使用正常 `data/bank.db`，没有修改业务源码或旧阶段包。普通 OS 子进程是本次并发测试载体，不是受限隔离／沙箱证据。零成功即使资金安全，也只能报告安全通过及可用性受影响；本次零成功轮数为 0，但不能据此宣称所有并发业务体验均无问题。
