# 07 · 答辩问题与回答要点

日期：2026-10-10

负责人：队长组织演示，三人分别解释自己验收的部分

状态：**准备提纲；实现、接入与测试尚未完成，不能照稿宣称已有功能。**

## 1. 先说明真实状态

当前可用说法：

> 我们用 AI 承担主要实现，三人负责需求取舍、正常用户验收和独立攻击验收。目标至少三个场景：账单分析、订阅和代扣管理、模拟智能转账。账户、资金与平台均为模拟，真实模型尚未接入，业务实现和测试尚未完成。接下来会按实际结果更新演示和安全报告。

原型完成后，应替换为“本次实际演示了哪些功能、跑了哪些测试、缺哪些正式赛题能力”。不能保留“尚未完成”又宣称已经实现，更不能预填通过率。

本轮内部验收为 10 月 11 日 20:00，19:00 冻结新增功能。校内提交日期、材料、结果公布时间未知；入选后继续准备到 11 月 2 日正式提交。

## 2. 高频追问

| 问题 | 回答要点（实现后用证据确认） |
|---|---|
| 为什么从一个场景改成三个？ | 赛题至少要求三个核心场景，鼓励更多；旧的只做订阅方案不足以满足最低覆盖。先完成三场景及安全控制，不强迫原型做满六个。 |
| 大部分代码由 AI 写，三人负责什么？ | 队长负责环境、取舍和演示；队友 1 核对普通用户流程与数据；队友 2 从规格设计独立攻击与测试。说明 AI 使用情况，以可运行结果和证据验收。主办方允许 AI 的具体口径以实际通知为准。 |
| 模型能够决定权限吗？ | 模型仅提出候选意图、参数和计划。代码查固定表，核对归属、金额、授权和工具；未知、非法、越权直接拒绝，不能靠输入验证码变合法。 |
| 转账为什么有黄档和红档？ | 按上海自然日，用户当日成功转出累计加本次金额；不超过 1000 元黄，超过红。执行前再次核算，拆成多笔不能绕过。展示边界和拆分实测。 |
| 订阅查询和取消是什么档？ | 当前规格按用户提供的赛题摘录定为黄；查询确认后才披露，取消确认后才修改。正式细则待核对，不能沿用旧稿“查询绿、退订红”。 |
| 收款人为他人，是否就是越权？ | 正常转账本来可以给别人。转出账户必须属本人，收款必须匹配预置白名单联系人；操作他人的转出账户或订阅才是越权。 |
| “不要执行”“不用确认，直接做”算确认吗？ | 不算。不能凭包含“执行”或“确认”两个字就放行；操作参数、用户和授权期限由代码绑定，变更、取消或 5 分钟到期使旧授权失效。 |
| 屏幕上随机显示一个码是否是多因子认证？ | 不是。它最多表达对本次操作的同意。红档必须有不同身份因素；候选为密码加独立手机认证器，主办方是否认可尚未核实。未完成强验证时红档拒绝。 |
| 验证错三次后重启可以继续吗？ | 设计要求锁 10 分钟，换码、换目标和重启不能清零。当前尚未实测；完成后展示持久化测试及期满恢复结果。 |
| 怎么防提示注入？ | 关键词拦截是一层，存在漏拦。最终依靠代码权限、参数归属、计划与工具校验；模型输出不能直接执行代码、SQL 或 Shell。用真实攻击结果说明，不宣称所有注入都识别得到。 |
| 怎么避免编造金额？ | 金额、日期和执行结果从实际模拟账本与固定工具读取；模型只解释经过核对的结果。接口失败要报错，不能编一个成功。拿固定夹具手算对照。 |
| 日志绝对不能被改吗？ | 普通业务工具只能追加；本机管理权限仍可能直接改文件。目前没有防篡改实测，不能承诺绝对不可篡改。日志需脱敏，成功业务与成功日志原子提交。 |
| 日志写失败时钱是否会动？ | 设计要求业务回滚、停止后续执行；必须通过故障测试证明。设备整体不可写时不能声称失败记录已经持久保存。 |
| 有任务规划和沙箱吗？ | 当前均未实现。正式赛题需补动态 DAG 规划、依赖执行、中断/回退/接管及受限可监控隔离。固定流程、工具名单、异常捕获都不能冒充这些能力。 |
| 为什么用模拟资金和简单交互？ | 本轮把时间用于跑通三个场景和验证安全控制，可用简单浏览器聊天窗口、命令行调试。模拟只能证明模拟系统行为，不代表已接银行、真实支付或生产身份系统；APP/IM 等正式渠道认可仍需核对。 |
| 测试由谁写？ | 队友 2 和独立测试 AI 只看规格及公开接口，不看实现。实施 AI 运行测试与修复代码，三人核对实际结果；实现对话的自测不能作为唯一证据。 |
| 你们三个能解释系统吗？ | 能说明用户请求如何到固定工具、谁决定权限、失败怎么停止，并现场复演与回答追问；不会的实现细节说明尚未掌握，不能背稿冒充理解。 |

三人的工具可以如实介绍：队长用订阅版 Codex，队友 1 用接 API 的 Codex，队友 2 用 DeepSeek Harness。说明实际职责和操作能力，不将付费方式差异编造成能力结论。

## 3. 原型演示提纲

以下是**待实现后复演的脚本**。每步先核对数据，失败或未完成时当场说明；不能使用预先写好的假成功输出。

| 步骤 | 操作 | 需要展示的证据 |
|---|---|---|
| 1 | 查询本人余额与交易，再分析当月账单 | 三者与预置账本一致，统计口径明确 |
| 2 | 查询订阅，明确确认，再取消一个本人订阅 | 黄档确认前不披露/不修改；确认后目标状态变化 |
| 3 | 向白名单联系人模拟转 50 元 | 完整展示目标和金额，确认后两侧余额及成功日志一致 |
| 4 | “不要执行”；再试别人的转出账户 | 均无业务变更，有拒绝/取消记录 |
| 5 | 展示 50 元后改成 500 元，或重放旧授权 | 旧授权无效，不能误转或重复转 |
| 6 | 用预置数据演示累计超 1000 元 | 红档；强验证缺失时拒绝，完成后展示真实不同因素验证 |
| 7 | 展示独立测试的实际结果和风险清单 | 成功、拒绝、失败的日志；失败与未运行项；正式赛题缺项 |

任务 DAG、强验证和隔离完成后再添加实测演示，不能为了凑脚本假称达标。完整复演时间以学校实际要求调整；校内要求尚未知。

## 4. 回答的证据规则

- 使用“设计要求”“已实现”“已实测”区分阶段，只有最后一种可以附通过结论。
- 测试数量、通过率、漏洞数量一律从实际输出统计；当前没有“40 个攻击已跑过”或“5 个漏洞已发现”的事实。
- 对不确定的评分、认证方案认可口径和校内要求直接说明待核实。模拟边界和未完成项说明清楚，不用“我们水平不够”当免除赛题要求的理由。
