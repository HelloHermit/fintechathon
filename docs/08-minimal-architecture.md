## 一、总体形态

**一个程序文件、五组普通函数、一个本地数据库。**

**五组函数 = 五个工位**：接待、审查、确认、办理、记账。首版全部放在 `main.py` 里，**各自只负责自己的事。**
**★ 但"一个程序文件"不等于"一个代码文件"**：P1 的 `init_db.py` 和 P5 的 `audit.py` 是**基础设施，仍然独立成文件**（见第五节目录结构、`分工表.md` 工作包表）。

**最小版约定**：
- 命令行界面
- 固定测试用户 `u001` + 模拟数据
- **先用固定短语识别意图**（★ 明确标注"**尚未接入 AI 模型**"）
- 模拟退订**只改本地记录，不连真实平台**

**★ "尚未接入 AI 模型"这句话必须在答辩时说。**
**为什么**：赛题是"AI 智能体"赛道。如果不说，评委可能认为我们假装接了模型；**主动说清楚，反而证明我们知道自己在做什么、知道这一步是"以后要接"而不是"忘了接"。**

## 二、五个模块，每个模块三句话

### 模块 1 · 输入与意图识别

- **它做什么**：读取用户原话，**先用代码拦截注入关键词**，再识别支持的意图
- **输入输出**：输入＝用户原话；输出＝「意图＋参数」，或"无法识别 / 需要补充信息"
- **它可能出的错**：听错动作、选错订阅
- **★ 约束**：**遇到多个意图、多个候选目标时，必须让用户重新选择，不能猜着执行**

### 模块 2 · 权限与参数检查

- **它做什么**：检查意图是否已被明确支持 → 参数是否合法 → 记录是否属于当前用户 → **再查代码里固定的档位表**
- **输入输出**：输入＝候选意图和参数；输出＝`green`/`yellow`/`red`，或拒绝理由
- **它可能出的错**：漏掉归属检查或参数检查
- **★ 约束**：**所有执行入口都必须经过检查；未知操作不能靠确认码获得执行资格**

### 模块 3 · 确认与失败锁定

- **它做什么**：管理黄色档的明确同意、红色档的 6 位确认码、连续 3 次失败后锁定 10 分钟
- **输入输出**：输入＝已检查过的操作 + 用户回应；输出＝允许执行 / 等待确认 / 取消 / 超时 / 锁定
- **它可能出的错**：让旧码确认新目标；让重启清掉失败次数
- **★ 约束**：**确认必须绑定具体操作；失败次数和解锁时间必须保存到数据库**

### 模块 4 · 业务执行与数据保存

- **它做什么**：通过固定的业务函数查询订阅和账单，或执行已经确认过的本地修改
- **输入输出**：输入＝通过检查及必要确认的操作；输出＝查询结果或修改结果
- **★ 金额统一用整数分**
- **它可能出的错**：算错支出口径、重复执行
- **★ 约束**：①**本月实际花费只统计已发生账单** ②**退订不能删除历史支出** ③**成功执行后确认立即失效**

### 模块 5 · 审计记录

- **它做什么**：追加记录查询、待确认、成功、拒绝、验证失败、取消、超时等结果
- **输入输出**：输入＝用户/时间/原话/意图/档位/参数/处理结果；输出＝一条新日志
- **它可能出的错**：保存失败
- **★ 约束**：**业务修改与成功日志必须一起保存；保存失败就撤回本次修改并停止后续业务处理**

## 三、数据流（每一步的输入输出）

```text
用户输入
   ↓
① 注入拦截 → 意图识别
   ↓
② 白名单、参数、归属检查 → 固定表判档
   ↓
③ 绿色直接通过；黄色等同意；红色等确认码
   ↓
④ 执行固定业务函数
   ↓
⑤ 追加审计记录 → 展示结果

任何一步拒绝、失败、取消或超时 → ⑤ 追加审计记录
需要确认 → 展示具体操作 → 接收下一条用户输入 → ③ 验证
```

| 步骤 | 输入 | 输出 |
|---|---|---|
| 输入与识别 | 用户原话，例如"退订视频会员" | 模拟退订意图 + 候选订阅；**没有唯一目标就要求选择** |
| 权限判定 | 意图、参数、当前用户、本地记录 | 唯一订阅编号 + 合法参数 + 固定档位；**检查不通过则拒绝** |
| 执行或确认 | 已通过检查的具体操作 | 查询直接执行；修改先展示**目标/动作/影响**，等待相应确认 |
| 业务办理 | 绑定当前操作的**有效**确认 | 本地结果，例如把指定记录标记为已退订 |
| 审计记录 | 本次处理的经过和结果 | 新日志；**业务修改与成功日志一起保存后，才展示成功** |

**★ 两处拦截点的位置（这是全文最要紧的一处）**：
- **注入关键词拦截** 在 **① 的意图识别之前**
- **白名单 / 参数 / 归属检查** 在 **② 的档位判定之前**
- **★ 「直接拒绝」发生在 ② ，不进入 ③ 的确认流程**（细则见 `docs/01` 第三节）

## 四、★ 确认机制：像签一张写清内容的申请单

**单上至少写**：用户、动作、订阅编号、参数、到期时间。
**不能只记"用户刚才说过同意"。**

| 规则 | 内容 |
|---|---|
| 单请求 | **同时只保留一个待确认请求**，有效期 5 分钟 |
| 即时失效 | 取消、换目标、改参数、提出另一操作 → **原确认立即失效** |
| 黄色档判断 | 按**完整回应**判断同意；**不能因为「不要执行」含"执行"就放行** |
| 红色档核对 | 用代码生成并显示的 6 位确认码，**按完整字符串核对** |
| 失败计数 | 按「**用户＋操作类型**」保存；**换码、换目标、取消、重启都不清零**；验证成功或锁定期满才清零 |
| 退出行为 | 程序退出后**待确认请求失效**，但**数据库中的失败次数和锁定时间保留** |
| 执行前复检 | 执行前**再次检查**归属、参数、锁定状态、确认是否仍然有效 |

**★ 一句必须说清的边界**（答辩时要主动讲）：

> 这里显示的确认码**只能演示"用户明确确认"，不能证明身份，也不是第二种身份认证因素。**
> 模拟退订用红档，是为了**演示严格的确认流程**；
> **不能因此声称"本地状态修改本身不可逆"。**

**★ 为什么这句重要**：`docs/04-known-risks.md` 里我们已经承认"没做多因子认证"。**如果在这里又把确认码说成"安全认证"，等于前后矛盾。**主动划清这条线，比被追问出来强。

## 六、★ 启动与初始化（一处容易出错的地方）

**启动时由 `main.py` 建立缺少的表，且只在首次初始化时加入示例数据。**

- **再次启动不能重置日志或锁定状态**
- 数据库保存：**订阅、历史账单、验证失败次数、解锁时间、审计日志**

**★ 为什么这条要单独写**：
这是**"重启清掉失败次数"这个漏洞的落点**。如果 `main.py` 每次启动都重建表或重灌数据，**熔断就被绕过了**——而且**不会报错**，功能看起来完全正常。

**测试点**：连续失败 3 次 → 关掉程序 → 重开 → **再试仍然是被锁的**。

## 七、★ 最脆弱的两个环节（A 的判断，我认可）

### 脆弱点 1 · 意图识别到执行的边界

**问题**：
- 关键词拦截会**漏掉换一种说法的攻击**
- 识别器可能**选错订阅**——即使档位判对了，**执行错目标仍然有问题**

**必须做的四件事**：
1. 使用**固定允许表**（白名单）
2. 使用**唯一订阅编号**（不是靠名字匹配）
3. **参数及归属检查**
4. **向用户展示具体目标**

**★ 一条前瞻约束**：**以后接入模型时，模型也只能接收候选意图和参数，不能执行模型生成的命令。**

### 脆弱点 2 · 确认到执行、保存的衔接

**问题**：旧码、换目标、重新申请、重启、保存失败——**都可能让"确认过了"和"实际办理的事"不一致。**

**必须做的四件事**：
1. **绑定操作**（确认对应具体哪个操作）
2. **让旧确认失效**（取消/换目标/改参数）
3. **持久保存锁定**（数据库，不是内存）
4. **业务修改与成功日志一起保存**

**A 用的类比，很准，可以直接拿去讲**：
> **办理手续和盖章必须一起完成，不能只完成其中一个。**
