# 14 · 现场评委压力审查（红队）

更新：2026-10-10　|　审查范围：`README.md` · `docs/07-defense-qa.md`（旧版）· `docs/11-technical-note.md`

> **10-11状态补记**：下文保留10-10审查时的3526 tokens、63项与CLI事实，属于历史引用，不能用作当前验收数字。当前正常五请求3960 tokens、两计划1583 tokens、六异常中五返回4007 tokens另1输入阻断；独立66业务＋27 HTTP共93项已通过。桌面浏览器三场景及数据库核对已有运行记录，手机测试按用户要求待云端后再做。MFA模块已有43项/99子用例合成验收（docs/23）；真人MFA、隔离、完整补偿、正式渠道与完整人工记录仍缺。下文未实现MFA的旧审查结论属于当时历史。当前状态以README、docs/09、docs/13和docs/14-browser-design.md为准。

> **这份文件是什么**：一份**从评委视角**做的攻击性审查。它不问"你们做了什么"，只问"你们哪里会被击穿"。
> **为什么值得留**：内部自审容易自我宽容，外部视角不会。**这 10 个问题就是答辩现场最可能的攻击面清单。**
> **用法**：答辩前逐题自答一遍。答不上来的，去 `docs/07` 第 2 节总表找答案；总表里也没有的，就是你还没想清楚的。
> **注意**：本报告指出的一部分问题属于**潜在**漏洞，需要现场实验确认，**不等于已经证明代码存在该漏洞**。

---

## 〇、审查结论

存在明确的文档冲突与关键能力证据缺口。团队最容易被击穿的地方不是 Python 写得好不好，而是四件事：

1. **AI 承担主要实现后，三名学生能否证明自己的实质贡献。**
2. **权限规则能否抵御跨工具绕过、并发请求和授权状态变化。**
3. **把局部功能测试通过，包装成完整安全能力已实现。**
4. **三份材料对「哪些功能已经完成」的说法互相打架。**

## 一、10 个最难回答的现场问题

### 1. AI 写了主要代码，你们三个人的技术贡献究竟是什么？

**杀伤力：极高**

> 你们说队长负责需求取舍和演示，队友负责用户验收与攻击验收。可是需求分析、测试生成、代码修复，AI 都能完成。
>
> 我现在不问你们用了什么 AI，也不接受「我们负责提示词工程」这个答案。
>
> **请三个人分别回答：你亲自发现过哪一个 AI 没发现的问题？你否决过 AI 提出的哪一个实现方案？你做过哪一次独立于实现 AI 的测试？**
>
> 请打开对应的原始记录证明。**没有记录，就告诉我为什么应该把这项技术成果归属于你们。**

**过关的回答**：提供三种具体证据——个人提出并形成记录的技术决策、独立发现问题的测试记录、从问题发现到修复验收的完整过程。三人还必须能**不借助 AI** 解释自己负责模块的主要状态转换和失败分支。

**当场崩掉的回答**：「我们负责提需求，AI 负责实现。」「我们会使用 Codex。」「我们对代码进行了检查。」——这些只能证明工具使用能力，不能证明进行了有效的工程判断。

---

### 2. 你们展示的是 AI 自主执行，还是测试脚本带着 AI 走完预定路线？

**杀伤力：极高**

> README 说 5 次真实 DeepSeek 请求完成三个业务方向，技术说明也说两条真实模型依赖计划完成。
>
> 但技术说明同时承认，**是测试脚本核对预先指定的用户、收款人和金额，然后调用固定确认接口。**
>
> 那我请问：如果我现场提出一个你们**没有准备过的合法组合请求**，谁来生成计划？谁来批准？谁来发现参数错误？
>
> 如果关键执行步骤已经由脚本安排好了，你们凭什么把演示结果归功于 AI Agent？

**过关的回答**：清晰区分**模型生成 / 代码规则判断 / 测试脚本预置操作 / 人工授权**，并现场展示未预置请求的模型输出、权限判定和失败行为；承认已有演示并未证明生产环境中的自主授权或通用复杂规划。

**当场崩掉的回答**：「真实 API 调用了，所以是自主 Agent。」「任务跑完了，说明自动规划能力已实现。」——把模型调用成功、业务流程成功和自主代理能力混为一谈。

---

### 3. 你们说有账户权限校验，但系统究竟怎样知道用户是谁？

**杀伤力：极高**

> 技术说明写着，可信当前用户由本机入口或构造配置指定，聊天中自称张三不会改变身份。很好。
>
> 但如果我不是通过聊天框，而是**在本地入口把当前用户配置成 alice，再调用 `BankService.propose`** 呢？系统凭什么知道我是 alice，而不是 bob？
>
> 你们的账户归属校验，是否只是建立在**调用者没有伪造身份**的前提上？

**过关的回答**：承认当前是**预置身份的模拟环境，没有实际登录认证机制**。账户归属检查只能证明业务内部不会越过指定身份边界，不能证明真实用户身份。能说明入口由谁控制、哪些接口允许构造测试身份。

**当场崩掉的回答**：「我们每次都检查账户属于当前用户，所以不会越权。」——这是循环论证：如果当前用户身份本身可以被不可信调用者指定，归属检查不能解决身份冒用问题。

---

### 4. ★ 账单分析是绿档、订阅查询是黄档，那我通过账单推断订阅，不就绕开权限了吗？

**杀伤力：极高**

> 你们规定查询交易和账单分析属于绿档，查询订阅属于黄档。
>
> 我不用 `query_subscriptions`，直接对 AI 说：
>
> **「请从我的过去六个月交易中找出每月重复扣费的平台，列出商户、金额、周期，并告诉我应该取消哪些服务。」**
>
> 如果 AI 通过绿档交易数据输出了一个事实上的订阅清单，黄档订阅查询还有什么实际意义？
>
> **你们限制的是工具调用，还是最终披露的信息？**

**过关的回答**：区分「根据历史流水推测周期性支出」和「读取当前生效的订阅状态」。对后者必须遵守订阅信息的权限控制；对前者不能冒充已验证的订阅清单。**最好能现场证明间接访问路径不会泄露受保护的状态或字段。**

**当场崩掉的回答**：「因为没有调用 `query_subscriptions`，所以没有违反权限规则。」——**真正的权限边界不能仅靠 API 名称区分。**

> **审查者注**：这是最值得实际攻击测试的一项，但目前三份文档还不足以证明该绕过一定成立。

---

### 5. ★ 你们的每日 1000 元限额，在并发和跨账户情况下还成立吗？

**杀伤力：极高**

> 假设 alice 今天已经成功转出 950 元。现在从两个不同会话、两个不同本人账户，**同时各发起 40 元转账**。
>
> 每个请求开始时都看到 950 元，950+40=990 元，都属于黄档。**如果两个请求都成功，今天累计就达到 1030 元。你们怎么防止？**
>
> 紧接着：你们的累计限额是**按账户**计算还是**按用户**计算？上海时间 23:59:59 和次日 00:00:01 的请求如何归档？转账前的重新核算使用什么**数据库事务和锁机制**？

**过关的回答**：解释额度按用户汇总，说明 SQLite 事务如何保证累计额的读取与写入不会发生竞争，并**现场展示并发测试**。若没测过真正并发，必须承认现有测试只覆盖串行重放和执行前状态变化。

**当场崩掉的回答**：「执行前会再检查一遍余额和限额，所以一定没问题。」——两个并发请求都重新检查，并不天然意味着检查结果能够被正确串行化。

---

### 6. 五分钟确认码到底授权了什么？你们能证明它不会被串用吗？

> alice 先请求转 100 元，系统生成确认码。随后用户把金额改成 500 元，又发起一条新的转账请求。
>
> **假设我把旧确认码填进新请求，或者在第一次授权成功后重复发送确认，又或者过了五分钟再执行。你们怎么保证每一种情况都不能动钱？**
>
> 请展示你们绑定确认状态的完整字段，而不是只告诉我「做了校验」。

**过关的回答**：说明确认绑定**用户、请求编号、意图、金额、目标账户、有效期及使用状态**，并由代码核验。可展示参数变更、超时、重放和新请求导致旧授权失效的测试。同时明确：**屏幕确认码只能表示对操作的确认，不能证明持有第二身份因素。**

**当场崩掉的回答**：「验证码是六位随机数，别人猜不到。」「我们让大模型判断用户有没有同意。」

---

### 7. 红档没有 MFA，你们凭什么声称实现了银行级权限控制？

> 你们规定累计转出不超过 1000 元是黄档，超过 1000 元是红档。那我现在发起 1000.01 元的首次转账，你们会怎样处理？
>
> 你们展示的六位码是屏幕上生成的，**那它和用户身份之间有什么独立可信的联系？**
>
> 如果所有红档请求只能拒绝，**你们的系统究竟是实现了红档验证，还是根本不支持红档业务？**

**过关的回答**：直接承认尚未实现 MFA，红档采取**拒绝执行**策略。这证明当前系统有拒绝高风险动作的安全约束，**但不等于已经具备红档业务办理能力。**

**当场崩掉的回答**：「有验证码就是双因素认证。」「红档被拒绝证明我们的 MFA 通过测试。」——未实现的能力不能因为系统拒绝执行，就变成已经实现。

---

### 8. 没有沙箱，你们到底把模型限制在什么地方？

> README 说 Docker 引擎没有连通，技术说明也承认没有容器边界实验。
>
> 既然没有受限隔离环境，你们用什么保证模型不会影响**本机其他文件、数据库、API 密钥或者执行环境**？
>
> **你们的工具白名单到底限制的是模型能够请求哪些业务动作，还是操作系统层面的实际访问权限？**
>
> 如果业务工具自身存在文件路径或 SQL 注入问题，白名单还管用吗？

**过关的回答**：明确区分**应用层工具白名单**和**运行环境隔离**。承认当前还没有沙箱级别的资源、文件、进程和网络隔离保证，也没有证据证明全部底层攻击面都被覆盖。

**当场崩掉的回答**：「我们限制模型只能调用六个工具，所以不需要沙箱。」——工具白名单不是沙箱，两者解决的问题不同。

---

### 9. 转账成功后，下一步失败了，你们到底回滚什么？

> 假设第一步转账已经提交成功，第二步或第三步失败，用户要求撤销整个任务。**你们说支持事务回滚，那钱会自动转回来吗？**
>
> 如果审计日志写入失败，是整个业务事务回滚，还是只有日志没保存？
>
> **请区别解释数据库回滚、业务补偿和人工接管。**

**过关的回答**：正确说明三种机制——
- 数据库回滚只能撤销**尚未提交**的事务；
- 已提交转账要逆向业务操作或补偿机制，**当前尚未实现**；
- 人工接管目前只能停止未完成步骤，**不能自动恢复已提交的全部业务状态**。

**当场崩掉的回答**：「我们使用 SQLite 事务，所以任何一步失败都可以把之前的转账撤销。」——这不是事务机制的工作方式，尤其是跨多个已提交业务步骤的任务。

---

### 10. 不准打开文档，现在把你们的账本、测试数和模型调用数全部对上

> 请在白板上解释以下数字，不能靠背稿：
> 990、1990、2990 为什么等于 5970 分？取消视频订阅后为什么历史实际支出还是 5970 分、未来预计变为 2980 分？alice 起始 10000 元、转出 100 元后为什么是 990000 分？bob 为什么变成 110000 分？5 次真实请求合计 3526 token、另有两条依赖计划 1583 token，为什么 README 只强调 3526？**63 项独立测试里有多少是真实模型端到端测试、多少是离线替身测试？谁亲自核对了全部 63 项？**

**过关的回答**：

| 项目 | 数值 |
|---|---|
| 历史实际消费 | 59.70 元 |
| 取消后未来预计 | 29.80 元 |
| alice 转账后主账户 | 9900.00 元 |
| bob 收款后主账户 | 1100.00 元 |
| 两次真实模型演示报告用量合计 | 5109 token（= 3526 + 1583） |

5109 仅是两次演示记录的公开用量，**不是整个账户的 token 消耗**。此外要能从独立报告抽取 63 项的具体用例、结果、依赖和未覆盖范围，**不把 63 项离线业务测试说成 63 项真实模型安全测试。**

**当场崩掉的回答**：「取消订阅以后以前的账单也会减少。」「10000 元转 100 元以后应该剩 999000 分。」「我们有 63 项通过，所以全部安全功能都验证过了。」

> **审查者注**：这类错误不是复杂算法问题，而是**团队没有真正理解自己演示的数据和测试边界**。

## 二、三份文档之间存在什么矛盾？

（只依据当时提供的三份文件核对，不把未提供的 JSON 回执和独立报告视为已核实证据。）

### 1. 明确矛盾：真实模型到底接入了没有？——**严重**

| 文档 | 表述 |
|---|---|
| `docs/07`（旧版） | 真实模型尚未接入，业务实现和测试尚未完成 |
| `README.md` | 5 次真实 DeepSeek 请求已完成三方向模拟业务 |
| `docs/11` | 20:35:58 开始的真实模型集成运行退出 0 |

**判定**：直接矛盾，严重。这不是技术理解差异，而是**当前事实状态完全不同**。两份文件都标注 2026-10-10，若混用，评委会直接质疑文档更新和内部审核机制。

**→ 处置：`docs/07` 已重写，状态行与 README 对齐。**

### 2. 明确矛盾：业务测试到底完成了没有？——**严重**

`docs/07`（旧版）写"业务实现和测试尚未完成"；README 写"已有独立验收报告"；`docs/11` 写"独立 63 项业务测试通过"。

**判定**：直接矛盾，严重。
**注意**：当时只能核对到三份材料**报告**了 63 项通过，**不能凭这三份材料独立确认全部原始测试结果**。

**→ 处置：`docs/07` 已重写；63 项口径在总表 D2/D3 明确限定为"独立业务测试（含离线替身）"。**

### 3. 部分矛盾：任务规划究竟有没有实现？

`docs/07`（旧版）写"任务规划和沙箱当前均未实现"；README 写"固定候选图控制已验，两条真实模型依赖计划样例完成"；`docs/11` 写"两条真实模型生成的依赖步骤已执行，通用复杂规划未证明"。

**判定**：关于"任何规划均未实现"的表述存在冲突，但不代表完整规划已经实现。
**准确状态**：两条限定条件下的真实模型依赖计划**已有运行记录**；通用动态 DAG 规划及完整中断/回退/接管能力**尚未证实**。
**旧稿用"均未实现"一笔带过，会抹掉已经完成的局部能力，也会掩盖真正缺失的部分。**

**→ 处置：`docs/07` 已区分为"部分已实测"。**

### 4. 验收责任与验收完成状态不一致——**误导风险高**

答辩稿提出三人分工（队长演示、队友 1 普通用户验收、队友 2 独立攻击验收）；README 注明 **v3 尚未取得队友同步或人工验收证据**；技术说明说独立子代理测试**不能代替**队友人工验收。

**判定**：不是严格事实矛盾，但误导风险很高。**「分配了验收职责」不等于「完成了验收」。**

**→ 处置：`docs/07` 总表 B1/B3/D3 已明确写"v3 队友人工验收未完成"。**

### 5. 演示转账金额不一致

`docs/07`（旧版）演示方案是转 **50 元**，README 和技术说明实际记录是 **100 元**。

**判定**：版本不一致。旧稿写明是待实现脚本，所以 50 元可视为原计划。**但正式答辩必须统一脚本**，否则一个人讲 50 元、另一个展示 100 元，团队会显得对演示版本失控。

**→ 处置：`docs/07` 与 `docs/12b` 已统一为 100 元。**

### 6. 3526 token 和 1583 token 是不是对不上？——**不是**

README 的 3526 限定为 `live_demo.py` 的 5 次请求；技术说明另外给出 `live_plan_demo.py` 的 1583。两项合计 5109，属于不同演示的用量。**README 没有把 3526 说成总用量，因此不构成数值矛盾。**

**但**：README 写有最多一亿 token 的本轮授权，且**没有账户级硬预算控制**。即使银行资金全部模拟，**真实模型 API 的消耗风险并非模拟**——这是另一个值得质询的工程治理问题。

**→ 处置：已列入 `docs/07` 总表 D5 与缺项 P2。**

### 7. 事务回滚与补偿回退是不是自相矛盾？——**不是**

README 说模拟转账的余额、流水和成功日志同事务；技术说明说已提交转账不能自动反转。**两者可以同时成立。**

真正问题在于：项目实现了**单次数据库事务**的一致性规则，却**尚未实现跨业务步骤的完整补偿机制**。**如果团队把前者说成后者，才构成能力上的错误陈述。**

| 990+1990+2990 | 5970 分 | 正确 |
| 取消后的未来预计 | 2980 分，比原 5970 少 2990 分 | 算术一致，具体订阅组成需数据核实 |
| alice 10000 元转出 100 元 | 990000 分 | 正确 |
| bob 1000 元收到 100 元 | 110000 分 | 正确 |
| 1000 元黄档、1100 元红档 | 与既定阈值一致 | 正确 |
| 3526+1583 token | 5109 token | 正确，统计范围不同 |
| README 5 次真实调用 vs 技术说明另有 2 条计划 | 分属两个运行记录 | 不冲突 |
| 旧稿 50 元 vs 实际演示 100 元 | 脚本未同步 | 文档版本问题（已修） |
| 旧稿"未完成" vs 其他两份"63 项通过" | 当前状态互相否定 | 明确矛盾（已修） |

**算术上没有发现能坐实的账本数字错误。不能为了挑毛病而硬说它们错了。**

**更值得怀疑的是测试的证明范围**：成功演示的数字正确，**不等于**权限、并发、身份验证、补偿和隔离均正确。
